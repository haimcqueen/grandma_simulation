# World Labs integration: findings and implementation readiness

Research date: **2026-09-05**. Status: **trying** — the sample viewer was tested; integration choices below are **proposed**, not team consensus.

## Decision at a glance

We have enough evidence to begin a bounded realistic-room implementation once its scope and generation are approved. No broad research phase is needed. Two focused engineering checks remain: Mint's actual RAD streaming/export contract, and correct occlusion of dynamic characters without damaging the splat image. Exact-house integration also requires a finished house asset and checked dimensions.

The sample-loading experiment is complete. It does not establish Zillow reconstruction accuracy, navigation correctness inside a generated room, or physical realism.

## Verified sample findings

- **Compatibility passed:** Three.js 0.185.1 + Spark 2.1.0 + Vite 8.2.2 built and rendered in local headless Google Chrome.
- **Sample loaded:** 500,000 splats, 7,582,907-byte SPZ; matching 114,183-triangle collider, 2,976,256-byte GLB.
- **Local timings:** initial browser asset initialization measured 0.40–0.94 seconds across runs; warm reload about 0.23 seconds. The download script separately measured about 1.25 seconds for SPZ and 0.71 seconds for GLB. These are this machine/network's observations, not generation time or cold production delivery guarantees.
- **Frame cadence:** observed median 16.7 ms and p95 16.8 ms in the desktop run. These are request-animation-frame intervals at fixed views, not GPU timings or proof of mobile-device performance.
- **Orientation matters:** rotate BOTH sample SPZ and collider by 180 degrees around X. Raw/raw is mutually aligned but visually upside-down. An initial splat-only rotation created a major mismatch. This is a tested transform for these files only; do not apply it blindly to Mint's exported runtime.
- **Alignment remains approximate:** an 18-ray comparison from three view directions found 17 paired hits for both-flipped, median absolute ray-depth difference 0.0172 sample units, maximum 0.2209. The initial mixed transform had median 0.5614 and maximum 2.4374. These are heuristic splat-versus-triangle intersections, not surveyed landmark error. Original ray coordinates and results are retained in `.artifacts/alignment.json`; the View C camera was subsequently moved backward to show the marker more clearly.
- **Occlusion needs work:** the wireframe broadly follows doors, walls, and counters after correction. A naive depth-only copy of the coarse collider visibly clips the splat image even when aligned. It is OFF by default. Correct character occlusion needs a deliberate render-pass/depth strategy and checked geometry; this is not solved by merely making the collider invisible.
- **Scale unverified:** SPZ is version 2, and the GLB has no metric extras. Scale 1 is retained. Marker dimensions are 1.7 units tall and 0.56 wide, NOT a verified 1.7 metres. Floor height is sampled from the collider at the marker location; there is no uniform floor calibration.
- **Reliability:** a second asset load succeeds; Three.js texture count stays at 10 in the observed reload. This is a limited reload check, not a memory-leak proof. Missing/invalid sample data produces an actionable error. Desktop runtime has no console errors; Spark emits a Three.js Clock deprecation warning. Mobile viewport overflow is checked, but physical mobile hardware is untested.
- **Payload:** production JavaScript is approximately 5.55 MB / 1.93 MB gzip, before sample assets. The build emits a size advisory. For integration, load the realistic viewer on demand and evaluate streaming.


### Final recorded browser run

The retained `metrics.json` records 407 ms initial asset initialization and 265 ms warm reload. Median frame interval was 16.7 ms and p95 16.8 ms. The texture count was 10 before and after reload; reported geometry counts were 4 and 3. No console errors were recorded in the normal loading path. Earlier-run ranges above provide context; the retained JSON is the exact final run, not an average.

The orientation comparison predates the final View C camera adjustment. Its original rays are preserved separately. Do not compare a new camera's exact ray results against the older values as a regression threshold.

Use the floor plan to establish room connections and selected labeled dimensions. Current v1 furniture is illustrative and must not silently become the measured ground truth.

Keep the main home's living/kitchen references together; avoid mixing in the ADU kitchen. Listing area (2,611 sq ft) and floor-plan area (2,311 sq ft) disagree. Neither figure is sufficient to calibrate the whole generated scene. Reference photos and the floor plan are linked below, not bundled as generated-asset inputs.

A generated room may reproduce appearance while changing island placement, doorway width, or room connections. A preview is useful for aesthetic review, but only the finished 3D environment can establish usable coverage. Label the result as photo-guided and approximate unless stronger evidence supports reconstruction accuracy.

## Mint workflow confirmed from the connected tool definitions

- The MCP world-generation tool accepts direct image URLs, including up to six `source_images`. Its `source_url` field is provenance only; it does not extract listing photos.
- Generation requires a project when no existing chat is supplied. Account/project mutation and generation were not performed during the probe.
- Automatic mode proceeds to final generation by default. The proposed Zillow experiment uses review mode because the user wants to inspect the preview before final generation. Preview work may itself consume credits.
- The completed-world artifact manifest supplies a remote RAD runtime and corresponding GLB collider. This differs from our locally downloaded SPZ sample.
- The connected world-generation schema does not expose GLB geometry input or an explicit model selector. Chisel reference-geometry input is documented in direct Marble, not proven through this MCP interface.
- Retain returned job/asset identifiers and follow status updates. A timeout must not automatically trigger another generation request.

These are dated interface observations. Recheck the live tool schema at execution. Public REST documentation and MCP fields/limits are not interchangeable.

## Remaining checks and when to perform them

| Question | Smallest useful check | Before what? |
| --- | --- | --- |
| Can Mint's final world load in our browser? | Inspect one completed manifest; load RAD and collider; check browser requests, CORS/range delivery, and supplied transforms | Calling the Mint integration complete |
| Can the resident disappear correctly behind furniture? | Test a mesh in front of and behind a known surface; compare images with and without the character; test a deliberate depth/compositing strategy | Demonstrating realistic resident movement |
| Are units and floor height trustworthy? | Inspect metadata and compare several independently identifiable plan/photo landmarks; record any calibration assumptions | Transferring v1 speeds/clearances as metres |
| Does the environment preserve a usable task route? | Inspect floor continuity, island passages, and destination standing points; derive checked navigation footprints | Enabling movement in the generated house |
| Is the experience reliable on the demo device? | Measure cold loading and moving-camera frame cadence on the actual presentation machine; test reset and a failed load | Live demonstration |

The occlusion experiment can use the existing sample without generation spending. Mint delivery and Zillow fidelity checks need a suitable completed asset; another literature search cannot settle them.

## Proposed next implementation

1. Keep the current v1 demo runnable. Treat `v2/` as an experiment until the realistic route works.
2. Prepare a small set of overlapping main living/kitchen photos and a focused prompt. Get approval for the generation scope and credit budget before submitting them.
3. Generate one preview in review mode. Review it with the user; then approve, revise, or stop. Avoid a whole-house generation as the first dependency.
4. Load the approved final asset through the manifest contract. Establish transformations and calibration from evidence rather than copying this sample's rotation.
5. Validate one floor region and two destinations. Adapt navigation footprints to that environment instead of overlaying unchanged v1 geometry.
6. Add one independent editable obstruction, reliable character occlusion, and the existing task/pause/reset controls. Keep obstacles out of the baked background.
7. Add a better character and walking animation after the environment-to-navigation connection works.

If the generated room changes the layout too much, revisit the choice: authored geometry with improved materials/models, or a separate Chisel experiment. Neither fallback is automatically authorized by this proposal.
